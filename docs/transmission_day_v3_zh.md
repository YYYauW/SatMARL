# 光学卫星全天任务规划与设备开机时序

新版以完整24小时作为一次测试场景，点目标每次成像5秒。机动、稳定、设备启动与数据传输均使用连续秒时间戳；状态推进到实际事件时刻。成像载荷和数传设备分别管理开机段，一次开机只进行一次启动准备。

测试入口为 `scripts/run_transmission_load.py`，默认配置为 `configs/transmission_day_v3.json`，环境类为 `EventTransmissionEnv`。原两小时实验和v2配置继续保留；v2运行需显式指定其配置。

## 全天时间范围与目标需求

| 设置 | 当前值 |
|---|---|
| 起始时刻 | 2026-08-01 00:00:00 UTC |
| 单回合结束时刻 | 2026-08-02 00:00:00 UTC |
| 单回合物理时间 | 86400秒 |
| 点目标单次成像 | 5秒 |
| 请求释放时刻 | 分布在完整24小时内 |
| 单个请求的观测有效期 | 240—960秒，即4—16分钟 |
| 本地规划前瞻范围 | 900秒 |
| 卫星数量与目标数量 | N和M独立变化，延续交叉测试矩阵 |

每个请求仍携带一次观测的原始数据量和压缩后存储需求，压缩后为原始数据的四分之一。多次观测请求的每颗贡献卫星各自产生完整数据包。场景结束时分别统计观测成功和所需数据完整交付成功。

目标数量M现在表示一天内的请求总数。同一个M放在24小时和原两小时场景中，时间平均负载不同，结果图与文字需标明测试时长。

## 连续秒时间与事件推进

内部时间索引使用秒，可取小数值。配置中的 `step_duration_seconds=1` 定义时间单位，`max_steps=86400`定义物理时间上限。策略调用次数由实际事件序列决定，不固定为86400次。

状态更新节点包括成像载荷开机、启动完成、姿态准备各阶段、成像结束、数据包发送结束、地面接触开始/结束、请求释放/过期和协同预留过期。空闲等待期间可按5秒重新检查机会；候选几何信息每30秒更新。本地细化和已接纳活动的起止时刻可落在这些更新点之间。

轨道缓存目前每30秒采样一次，执行时按位置和速度进行三次Hermite插值，求取小数秒轨道状态。缓存采样间隔、候选集更新间隔、策略事件时刻分别记录。

地面接触以1秒扫描并细化仰角边界到0.01秒；本地成像起始搜索以5秒形成括区，再将可行起始边界细化到0.001秒。扫描可能遗漏短于扫描间隔的擦边可行区间；需要时可减小相应配置。点目标成像在起始及后续每一秒检查几何条件，直到第5秒。

## 机动与稳定时间

三轴角度变化分别计算，角速度曲线包含加速、可能的匀速和减速阶段。当前使用静止到静止的三角形或梯形角速度模型。对于单轴角度变化绝对值d、最大角速度w和最大角加速度a：

```text
d <= w²/a：T = 2 sqrt(d/a)
d >  w²/a：T = d/w + w/a
```

三轴可同时机动，总机动时间取三轴所需时间的最大值。机动完成后保留独立的稳定时间。成像结束时的指向作为下一次任务切换的起点。

| 参数 | 当前参考设置 | 来源范围 |
|---|---:|---|
| 最大角速度 | 1°/s | 国内敏捷规划公开算例参考 |
| 最大角加速度 | 0.25°/s² | 采用公开算例较小的减速度上限，构成对称保守设置 |
| 姿态稳定时间 | 5秒 | 同一敏捷规划公开算例参考 |
| 单次成像 | 5秒 | 本研究指定的点目标获取时长 |

例如，单轴切换10°时，机动时间为14秒，之后稳定5秒。机动14秒和稳定5秒各按实际值计时。下一目标的准确角度由它在计划成像时刻的轨道几何求出，实际计划还受太阳高度角、指向范围、存储、能量和请求期限约束。

机动规划参考：[一种针对敏捷卫星的在线调度方法 CN107290961A](https://patents.google.com/patent/CN107290961A/zh)。该算例采用1°/s、加速0.5°/s²、减速0.25°/s²、稳定5秒。本研究将两侧加速度统一为0.25°/s²。这组数值是规划参考工况，不代表所有中国光学卫星的实测姿控能力。

## 成像载荷一次开机连续获取多个目标

载荷冷启动准备时间当前设为60秒。一次启动准备完成后，载荷保持开机/待命，可以依次获取多个目标；各目标分别计算机动、稳定和5秒成像。当前取消了每个点目标之后固定30秒的强制冷却，`payload_cooldown_seconds=0`。

冷启动准备与姿态机动/稳定可并行，首次成像开始需同时满足：

```text
成像开始 >= 设备启动完成
成像开始 >= 机动结束 + 稳定时间
成像开始和结束均满足请求期限及观测几何
```

较晚的已接纳任务会安排在成像前60秒开机，避免因提前接纳任务而立即长时间开机。已有开机段中继续接纳目标时保持待命。最后一次已安排成像完成后，若240秒内没有继续执行的活动，则关闭载荷；下一次冷启动重新计准备时间。240秒是本研究待命策略的可配置参数。

分别导出成像次数、载荷冷启动次数、载荷累计开机时间与累计实际成像时间。一次开机可以对应多次成像。

## 数传窗口内一次启动连续发送数据

数传设备独立管理其开机状态。已有待传或已接纳成像的数据时，根据计算得到的星地接触安排启动准备。当前数传准备时间参考工况设为420秒，允许提前在接触开始之前完成。

数传准备完成且进入有效仰角窗口后，策略可以发起下传。一次会话会顺序处理多个目标的数据包；某个数据包传完可立即发送下一个。队列清空时释放接收天线，数传设备在当前开机段内保持待命；同一窗口内再有数据时继续发送，不重复启动。相邻地面站的接触及预开机区间重叠时，复用一个连续数传开机段。

数传准备可以在成像期间独立进行；实际成像和实际下传仍按当前单星活动互斥规则处理。载荷启动与数传启动分别计数。

900 Mbps标称码速率、0.8效率和10°—90°仰角掩膜沿用v2配置。数传发送结束时刻使用数据量除以净速率计算，可为小数秒。

60秒载荷提前开机和420秒数传准备参考了[遥感卫星多载荷普查观测自主任务方法](https://journal.bit.edu.cn/zr/cn/article/doi/10.15918/j.tbit1001-0645.2024.021)。原文描述载荷提前1分钟开机、数传复接调制器提前7分钟预热，以及任务间隔较小时保持待命。本研究用这组时序构成可调整的开机工况。原文的420秒属于该数传设备链的准备条件，不是对所有X频段发射机自身热机时长的规定，也不表示5秒点目标成像复制了原文的大幅宽普查载荷。

## 滚动成像预算与评价指标

用户指定的约束保持为：任意连续5400秒内，每颗卫星实际成像累计不超过1800秒。每次5秒成像按区间重叠量累计，已接纳的未来成像也计入预算。机动、稳定、预热、待命和数传时间分别记录。

| 输出 | 定义 |
|---|---|
| `simulated_seconds` | 已推进的物理秒数；完整回合应为86400 |
| `event_transitions` | 状态推进次数 |
| `observation_success_tasks` | 所需观测均已结束的请求数 |
| `observation_and_downlink_success_tasks` | 所需观测及其全部数据均已交付的请求数 |
| `imaging_startup_count` | 成像载荷冷启动次数 |
| `downlink_startup_count` | 数传设备冷启动次数 |
| `imaging_power_on_seconds` | 各卫星成像载荷开机时间之和，含启动/待命 |
| `radio_power_on_seconds` | 各卫星数传设备开机时间之和 |
| `max_rolling_imaging_seconds` | 任一卫星90分钟窗口内的最大累计成像时间 |

成像明细包含机动起点、机动秒数、稳定秒数、启动准备秒数、设备开机时刻、成像起止时刻和完整交付时刻。`radio_power_sessions`保留数传计划开机、实际开机、准备完成和开机段结束时刻。

归一化能量模型保留，太阳补充按实际经过时间积分；空闲和机动代价换算为每秒口径。原按MB下传奖励系数不变，正式重新训练前仍应统一奖励尺度。当前训练脚本尚未接入事件环境。

## 服务器运行

先安装v3更新包；不需要先安装v2。安装器支持原基线和已安装v2版本，并备份要更新的文件。碰到未识别的本地改动时停止。

```bash
conda activate satmarl
python ~/satmarl_transmission_v3_update/install.py --project ~/SatMARL
python ~/satmarl_transmission_v3_update/install.py --project ~/SatMARL --apply
cd ~/SatMARL
```

10分钟小规模检查：

```bash
python scripts/run_transmission_load.py \
  --config configs/transmission_day_v3.json \
  --run-root runs/transmission_event_v3_smoke \
  --policy priority --smoke
```

保留完整24小时的小规模检查：

```bash
python scripts/run_transmission_load.py \
  --config configs/transmission_day_v3.json \
  --run-root runs/transmission_event_v3_daycheck \
  --policy priority --full-day-smoke
```

先用一个旧模型做全天兼容性检查：

```bash
python -u scripts/run_transmission_load.py \
  --config configs/transmission_day_v3.json \
  --run-root runs/transmission_event_v3_model_check \
  --model-root runs/thousand_paper_suite/training \
  --methods full --training-seeds 701 \
  --satellites 512 --task-counts 6144 \
  --episodes 1 --device cuda
```

固定512颗卫星、改变全天目标总数：

```bash
python -u scripts/run_transmission_load.py \
  --config configs/transmission_day_v3.json \
  --run-root runs/transmission_event_v3_n512 \
  --model-root runs/thousand_paper_suite/training \
  --methods full,mappo,no_reservation --training-seeds 701,702 \
  --satellites 512 --task-counts 6144,12288,24576,49152 \
  --episodes 20 --device cuda
```

旧模型的候选/邻居宽度及预留开关从检查点读取，预留时长先按原物理步换算为秒。网络结构兼容性需在服务器验证；旧模型结果标记为新时间与资源条件下的迁移评估。不能用原训练命令假定已经在事件环境中重新训练。

输出目录继续包含模型/代码/场景哈希、逐回合指标、按训练种子汇总和成像/交付明细。参数或协议变化使用新的run-root，同一配置断点继续可附加 `--resume`。
